# NaTune folder, FLAC and storage task

## User outcome

Choose where future downloads go, obtain and play the intended lossless
recording when available, and gradually move selected existing downloads to the
chosen computer while reclaiming the corresponding phone space. Preserve the
current library, playlists, settings, explicitly kept albums and unfinished
work. A local copy alone does not reclaim lasting phone space.

## Done means

The user can use the real app action and choose its destination. A bounded
queue identifies each original rendition, verifies complete output and the
independently saved computer copy, and removes only the eligible unchanged
original. The temporary-overlap pool follows the user's 1,000,000,000-byte
selection. Interrupted or uncertain jobs recover without blind replay. Future
folder downloads, offline playback and FLAC selection/upgrade preserve song and
library identity; a codec label or prefix is not whole-file/recording proof.
The actual installation/data-handoff, rollback and user/device acceptance must
be demonstrated; a hosted build is not a release.

## Current reality

Runtime audio settings have an off-phone exact-APK build/static proof, but no
phone installation or playback proof. The selected-cache reader, local
MediaStore copy, full-stream native-FLAC verifier and journal have synthetic
joined-path checks; the latest results are in
`flac-folder-recovery-verification.json`. They do not supply the actual
app/journal/receiver binding or removal. The original app's private downloaded
cache is not accessible to a differently signed patch by assumption. No
current music copy, deletion or storage gain is claimed. Gboard is separately
owned; a pinned source join passed hosted library checks and an Android
cross-build without touching its index. `companion-source-join-verification.json`
records the exact join and its limits. The uninstalled folder/FLAC carrier
passed an exact public APK static comparison; its original native library is
4 KiB aligned. The replacement library now passes 16 KiB ELF layout and the
existing synthetic checks. A separate hosted finalization produced a stored,
aligned entry and passed a full ZIP-content and exact-original comparison;
Morphe's direct MPP output still needs that finalization. The evidence is in
`flac-finalized-carrier-verification.json` and `flac-16k-verification.json`.
The combined development profile joins that carrier with the existing audio
settings and passed an exact public APK comparison; see
`combined-dev-verification.json`. It is uninstalled and has no Move action.

## Remaining work packages

1. **Installation and data continuity — critical.** Establish a supported
   original-app handoff or compatible signer path, preserving downloads and
   configuration. Owner: NaTune, with the existing media operator for the
   stock export/receiver. Exit: a verified recoverable path for actual data.
2. **Actual app action and transaction — critical.** Bind selection, original
   cache/cancellation, destination, shared-budget admission and the existing
   encrypted journal to a real authenticated owner. Exit: an interruption-safe
   single-track phone proof, followed by a bounded queue.
3. **FLAC and future folder downloads — critical.** Bind provider/recording
   selection, complete codec/integrity verification, direct destination writing,
   offline playback mapping and safe verified replacement. Exit: actual app
   acceptance across the selected sources and supported formats.
4. **Computer transfer and source release — critical.** Reuse the existing Fuji
   operator and independent saved-file readback, then add scoped cache removal
   and recovery for the user's applicable selection. Exit: one verified eligible
   track and then a bounded batch with measured phone-space results.
5. **Packaging and rollback.** Join the current Gboard companion without
   replacing its manifests; build off-phone, verify the exact patched APK and
   only deploy through a proven data-preserving route. Exit: installed and
   user-attested behavior with a tested recovery path.

Reuse the app's actual cache owners, the existing encrypted identity/journal and
the existing Fuji receiver. Avoid parallel transport, duplicate staging and a
second model or media operator. Public FLAC decoder facilities may be reused
only after their exact input, bit depth, integrity and deployment contracts are
verified; no decoder selection or new phone dependency is claimed here.

## Next checkpoint and blockers

Integrate the real selected app action and journal/receiver once their original
authority and data-continuity interfaces exist. The shared Rust API boundary
was returned to the Gboard owner. The concrete app-to-journal expert review
is prepared; the existing Dot route is unverified, so that request remains
unsent. The same-signer/data-handoff and real app/journal/receiver interfaces
remain critical gaps. A useful completion ETA cannot yet be supported;
individual hosted checks usually take minutes, but neither their timing nor a
device deployment time is guaranteed.
